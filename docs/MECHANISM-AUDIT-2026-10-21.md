## 二、代码层面已确认问题

### P0-01：拖动睡着的鲸鱼仍可能被自动叫醒

**证据链：**

1. `pet/autonomy.py:182-184,974-992`：睡眠活动每约 500ms 检查一次 `_sleep_loop_active(SLEEP_ANIMATION)`；检测为假就 `_cancel_plan(awakened=True)`。
2. Overlay `pet/sprite_behavior.py:503-516`：`held_animation_active()` 明确要求 `sprite.interaction_state == INTERACTION_NORMAL`，在拖拽期间即使保持 `STATE_HELD`、动画没有变，仍返回 `False`。
3. 传统窗口 `pet/window.py:2875-2879,1800-1802`：`autonomy_sleep_loop_active()` 要求 `autonomy_ready()`，而 `_dragging=True` 或 `_physics_mode='drag'` 就让它变成 `False`。
4. 旧测试 `pet/tests/test_whale_sleep_drag_and_audit.py` 只检验拖拽入口不调用换绑，却**没有模拟 500ms 睡眠监测器在拖拽中运行**。

**独立复现：** Overlay 的 `held_animation_active()` 在 `interaction_state='normal'` 返回 `True`，仅把状态改为 `drag` 就返回 `False`，无需切换动画。下一轮看门狗会把这种“只是在移动位置”误判为“动画被打断”。

**修复建议：** 把“画面是否仍由 AI 持有”和“是否允许 AI 操作位置”拆成不同判断。睡眠健康检测只看受保护动画归属/素材是否仍播放，不用 `autonomy_ready` 和交互状态判断；真正被双击、抛掷、切角色才触发唤醒。新测试必须在模拟拖拽持续 2～3 秒时多次触发活动看门狗，并确认截止时间、生命记录不变。

### P0-02：Windows 系统睡眠/长时间卡住后，在线生命时间被吞掉

**源码：** `pet/life_state.py:151-160`：

```python
minutes = min(max(0.0, (stamp - self.updated_at) / 60.0), limit_minutes)
self.updated_at = stamp
```

`limit_minutes` 默认 60：超过 60 分钟的部分不会结算，却仍把 `updated_at` 推进到最新时间。`pet/autonomy.py:185-187,375-379` 的在线 30 秒时钟使用默认上限；`_cancel_plan()` 也调用同一方法。

**可运行复现：** 从困意 84 出发，模拟 8 小时后一次性调用 `advance(activity='nap')`，实际得到困意 **30**（只扣 `60 × 0.9 = 54`），而完整 8 小时睡眠按数值上限应降为 0。模拟尚且假设 8 小时都是睡眠；真实在线计划只维持约 20～35 分钟，跨越睡眠结束点需要按活动/时钟区间细分结算。

**修复建议：** 增加睡眠/恢复事件识别，按**墙上时间区间分段结算**，不能简单把 `limit_minutes` 调大就把整个停机间隔都算成 `nap`。建议重用离线结算时间分段器，并持久化在线活动截止墙上时间；恢复时分别计算“计划内睡眠、夜间自然睡眠、清醒”三段，保证不重复记账。

### P1-03：重复入睡的计划没有可靠持久化

**源码：** `pet/life_state.py:277-305` 中 `start_activity('nap')` 先更新 `sleep_until_at`，随后在最近一条相同事件不到 600 秒时 `return`，绕过最后的 `save(force=True)`。

**可运行复现：** 14:00 入睡、14:01 叫醒并保存、14:05 再入睡，此时内存里的 `sleep_until_at` 有值，但磁盘 `whale-life-state.json` 仍为 `null`。14:05 关机/闪退就无法补算第二段计划。

**修复建议：** 将持久化状态写入与“最近事件去重”完全分离：无论记录是否去重，只要睡眠截止日期或吃饭记账改变，都执行保存。新增“十分钟内重复睡、再次被叫醒、关机再启动”的回归测试。

### P1-04 / P1-05 / P1-06：睡眠语义和 AI 决策协议不一致

- `pet/activity_lifecycle.py:15-25,51-69` 限定在线夜晚 `nap` 为 20～35 分钟；`pet/life_state.py:26-27,189-265` 离线按 22:00～07:00 整段补算。这两套规则都按各自代码执行，但不是一致的作息体验。
- `pet/autonomy_intent.py:84,92-94`：`nap` 名称固定为“午睡”，而 `rest` 也可以选择真实的睡眠动画“原地小憩沉眠”。
- `pet/life_state.py:166-178`：正式 `nap` 降低困意 `0.9/分钟`，`rest` 则只降低 `0.075/分钟`，相差 **12 倍**；但画面可能都在播放睡眠素材。
- `pet/autonomy_intent.py:255-258` 提示模型“夜晚睡眠可以更长”，但是执行器最高仍为 35 分钟。提示词应基于本地活动配置构造或同步修改。

**修复建议：** 明确 `sleep`（夜间主睡眠）/`nap`（白天短睡）/`rest`（清醒放松）三种活动，不要让同一个“沉眠”素材以相差 12 倍的恢复规则运行；用户可双击叫醒，但不能单击/普通拖拽误醒。夜间主睡眠可以安排整夜，白天短睡保持 15～30 分钟。界面使用起床/午睡/夜间睡眠语义标签，不只换字面文案。

## 三、其他明显问题和优化机会

### P2-07：所谓“独立搭话”只在持续活动中启用

`pet/autonomy.py:502-524` 的 `_speech_tick()` 和 `_start_speech()` 都把 `not self._plan_active` 作为拒绝条件。闲置时即使等够可选的 3～6 分钟，也不进入自主搭话请求。若目标是“她会在待机时主动陪伴”，应允许单独的闲置搭话条件（仍遵守 DND、睡眠及 API 冷却）。这属于目标差异，不一定是技术故障。

### P2-08：失败重试间隔与错误提示

`pet/autonomy.py:571-572` 在发起请求前就预约下一次 3～6 分钟；`625-629` 遇到模型错误直接结束，不安排短暂重试。建议针对超时/临时网络故障做 30 秒起始、指数退避且有上限的重试；401/403/配置错误不应盲目重试。监控面板展示**脱敏**错误类别、HTTP 状态、重试时间，不记录 URL 密钥或原始上游响应。

### P2-09：传统窗口单击音效仍会响

`pet/window.py:3402-3410` 先播放按压/松开音效，之后才询问 `on_should_play_click` 是否允许点击。持续睡眠中的第一次单击虽不会切动画，但仍可能发声；Overlay 路径的守卫位于音效反馈之前 (`pet/overlay_shell.py:873-891`)。建议统一两种渲染模式的交互事务顺序：先判定是否允许点击，再决定播放动画、音效、发起 AI 回复。

### P2-10：活动名称与真实时间不匹配

`pet/autonomy_intent.py:84` 的 `ACTIVITY_CLIPS['nap']` 固定为“午睡”。清晨 7:30 或夜里睡也显示“午睡”。应让内部活动 ID 保持稳定、仅显示标签动态映射；不要在各模块随意改 `nap` 的内部名称。

### P2-11：回归测试自身路径有误

`pet/tests/test_autonomy_activity_time.py:14,25,85` 用 `Path(__file__).resolve().parents[1]` 当项目根，接着拼接 `pet/...`，导致实际尝试读取 `<project>/pet/pet/autonomy_monitor.py`。本轮执行相关文件时确实报 `FileNotFoundError`；应改为 `parents[2]` 或按 package import 定位。

### P2-12：时间异常路径值得单测

`WhaleLife.advance()` 在 `stamp < updated_at` 时直接回拨更新时间；`_load()` 对未来时间戳有窗口约束。夏令时切换、用户改系统时钟、跨时区切换及关机超过 24 小时等场景应覆盖，尤其须保证 `sleep_minutes` 不重复、不为负，`before/after` 与保存时间可对账。此项为**未验证的风险**，不等同于已发现确定性错误。

## 四、建议修复顺序与验收指标

| 批次 | 要一起修的内容 | 必须增加的回归场景 | 验收标准 |
| --- | --- | --- | --- |
| 第一批（必要） | 拖拽监控误醒 + 在线长时差补算 + 重复午睡持久化 | 两种模式睡着拖动 3 秒；Windows 系统休眠 8 小时；连续两次午睡后异常退出 | 拖动不取消计划，困意正确分段累计，再启动可恢复剩余午睡 |
| 第二批（机制统一） | 夜间主睡眠、午睡、清醒休息分层；标签与提示词同步 | 22:00～07:00 全程在线 vs 离线；白天 nap；夜间双击叫醒 | 在线/离线同类场景恢复值可解释，夜间不每 30 分钟无意义醒一次 |
| 第三批（体验与质量） | 闲置主动搭话策略、错误退避、单击音效、修复测试路径 | 4Router 超时/401；空闲无计划；传统与 Overlay 误触；全量测试 | 无重复 API 风暴、临时失败可恢复、两个渲染模式行为一致 |

**建议的统一设计：** 建立一个持久化生活时钟：时间轴分段记账（在线/离线共用）＋活动的唯一持有者与截止时间＋“移动位置不等于结束活动”的交互状态机。这样能同时解决现在最明显的三条故障链，而不是在每个 Qt 定时器上继续叠加特殊分支。
