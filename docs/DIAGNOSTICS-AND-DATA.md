# AI 决策状态面板、持久化与故障排查

> 对照：`pet/autonomy_monitor.py`、`pet/autonomy.py`、`pet/life_state.py`、`pet/chat/ai_settings_page.py`、`pet/config.py`。

## 1. 三类数据不要混淆

| 数据 | 文件 / 位置 | 存储内容 | 用途 |
| --- | --- | --- | --- |
| 生命状态 | 应用数据目录 `whale-life-state.json` | 四项生命值、`updated_at`、餐食、睡眠截止时间、生活事件、离线审计 | 生命值跨重启及夜间离线补算的真实依据 |
| AI 决策状态 | 应用数据目录 `autonomy-decision-status.json` | 是否开启、模型标识、请求/完成数量、活动/剩余时长、搭话倒计时、最近 5 条结果 | 设置页与桌宠进程间同步显示；属于诊断快照 |
| 动画循环偏好 | 项目根目录 `activity-loops.json`、`sleep-loop.json` | 每个动画的起止百分比 | 画面循环设置，不决定是否睡够或生命值恢复 |

这些都**不是**截图缓存、完整聊天记录或 API 密钥存储。应用数据目录通常由 `pet/config.py` 的 `Config.dir` 决定，不应误以为一定在 `2-Run-Windows.bat` 同级目录。设置页可以在独立进程运行，从 `autonomy-decision-status.json` 读取桌宠状态；运行进程才负责写它。

## 2. 状态面板有哪些指标？

| 项目 | 应当如何解读 |
| --- | --- |
| 运行状态 | 当前等待/请求中/执行持续活动/异常等，不是气泡文本 |
| 当前活动计时 | 活动名称、已进行/总时间、剩余时间、预计结束；阶段更新**不重置**截止时间 |
| AI 搭话与点击回应 | 最后状态和距离下次**判断**的剩余秒数；不是定时强制发言 |
| 精力/饥饿/困意/心情 | 数值来源于本地 `WhaleLife`；模型没有直接任意覆盖权限 |
| 最近生活经历 | 最近最多 12 条生活事件；不等于完整离线审计 |
| 请求次数 / 完成次数 | 包含主动决策与搭话请求的执行计数；不能直接当作单类 API 账单 |
| 最近动作 / 结果 / 错误 | 显示本地执行是否接受、解析是否有效、错误类型 |

监控快照中的 `activity_ends_at`、`next_decision_at`、`speech_next_at` 等为时间戳，界面负责倒计时显示。桌宠长时间未刷新共享状态时，独立设置进程会把状态标记为“可能已退出”；并不意味着生命值自动消失。

## 3. 常见问题诊断表

| 现象 | 首先检查 | 再检查 |
| --- | --- | --- |
| “搭话请求失败，约 321 秒后再判断” | 3～6 分钟是默认随机间隔，不是新的故障 | `last_error`、Provider 是否可用、网关实际请求记录 |
| AI 不自己动 | `autonomy_enabled` 是否开启、当前是否持续活动 | 模型/API 地址、请求/完成数、`last_error` |
| 点击没有触发模型 | 现在有持续活动吗？单击受保护、双击才打断 | 12 秒点击限频、气泡占用/免打扰、忙碌排队及 Provider |
| 工作播放同一片动画很久 | 当前阶段是否仍在有效 8 分钟工作计划中 | 是否只有一个可用素材，或阶段更新仍在等待 |
| 睡了 8 小时困意还是 84 | 查看 `offline_settlements[-1].night_sleep_minutes` 和 `before/after` | `updated_at`、时间窗口、是否其实在线短睡而非离线结算 |
| 清晨显示“午睡” | `ACTIVITY_CLIPS["nap"]` 的界面名称目前仍是“午睡” | 真实时长和生命值是否按对应活动运行 |
| 睡觉时拖动闪到悬空 | 当前运行代码是否已覆盖最新拖拽补丁 | 当前是温和拖动还是被判定为抛掷、窗口模式是否不同 |
| 右键菜单外点击不关闭 | Windows 专用外部点击监测代码是否已更新 | 先在 Windows 实机分别验收菜单主项、子菜单和别的软件窗口 |
| 当前活动到点却未立即切画面 | 正在播的素材可能需要自然收尾 | 是否有物理/用户交互优先级接管 |

错误面板通常记录**异常类型和可用 HTTP 状态码**，不是完整服务商响应。若要排查网关拒绝请求，需要同时查看 API 服务商控制台，并遮蔽密钥、含隐私的截图或聊天记录。

## 4. 离线审计如何核对？

示例：23:00 退出、次日 08:00 启动。应在新增加的 `offline_settlements` 记录中看到：

| 字段 | 预期解释 |
| --- | --- |
| `started_at` | 上一次持久状态结算时间，接近昨晚退出时间 |
| `settled_from_at` | 真正开始结算的时间（若超过 24 小时则裁到最近 24 小时） |
| `finished_at` | 本次启动结算时间 |
| `sleep_minutes` | 累计补算的睡眠时间，此例约 480 分钟 |
| `night_sleep_minutes` | 此例约 480 分钟 |
| `daytime_nap_minutes` | 未带未完成白天睡眠计划时应为 0 |
| `discarded_minutes` | 被 24 小时上限裁掉的时间 |
| `before` / `after` | 结算前/后四项生命值 |

若连续关机几天，只补算最近 24 小时，不应重放所有历史的夜晚。已结算时间立即写回 `updated_at`，重新启动不会重复领睡眠恢复。详见 [生命机制与速率](WHALE-LIFE-MECHANICS.md)。

## 5. 适合提交 Bug 时提供什么？

建议只提供以下**最少信息**：使用的补丁/源码版本、Windows 版本、传统窗口还是 Overlay、复现步骤、AI 状态面板里的错误类别、相关生命审计字段及开始/结束时间。

**不要直接发 API Key、完整模型请求、全屏截图或带私人聊天的全量配置**。状态 JSON 也可能包含活动名称和时间信息，分享前请确认这些信息是否适合公开。
